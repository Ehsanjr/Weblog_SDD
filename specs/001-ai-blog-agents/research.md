# پژوهش و تصمیم‌های طراحی

این تصمیم‌ها از PRD و `spec.md` استخراج شده‌اند. انتخاب فناوری جدید یا نیازمندی بیرونی به پروژه افزوده نشده است.

## تصمیم‌ها

### سرویس یکپارچه Spring Boot

- **تصمیم**: یک برنامه Java 17+ با Spring Boot 3.x و Maven.
- **دلیل**: پشته در PRD الزام شده و محصول یک REST API محلی با یک مرز عملیاتی است.
- **گزینه‌های بررسی‌شده**: ریزخدمت‌ها و فرانت‌اند؛ هر دو خارج از محدوده صریح‌اند.

### قرارداد و استقلال ایجنت‌ها

- **تصمیم**: قراردادهای ورودی/خروجی مشترک کوچک در `agent.contract`، پیاده‌سازی‌های جدا در `agent.writing` و `agent.review`، و اجرای آن‌ها فقط از orchestration برنامه.
- **دلیل**: مرز پکیج‌ها قابل آزمون می‌شود، ReviewAgent مخزن مقاله را نمی‌بیند و ایجنت‌ها همدیگر را فراخوانی نمی‌کنند.
- **گزینه‌های بررسی‌شده**: ارتباط مستقیم ایجنت‌ها یا دسترسی ReviewAgent به repository؛ هر دو خلاف PRD هستند.

### حالت MOCK و اتصال مدل

- **تصمیم**: دو adapter مستقل MOCK و REAL با انتخاب از `AGENT_MODE`؛ adapter واقعی از تنظیمات مستقل نویسنده/بازبین استفاده می‌کند و خروجی ساختاریافته را پیش از ذخیره اعتبارسنجی می‌کند.
- **دلیل**: اجرای اولیه باید بدون شبکه و کلید ممکن باشد و تست‌ها قطعی بمانند.
- **گزینه‌های بررسی‌شده**: فراخوانی سرویس مدل در زمان راه‌اندازی یا اجباری کردن کلید؛ مانع اجرای MOCK می‌شود.
- **جزئیات محدود**: کتابخانه HTTP خاصی در PRD تعیین نشده است؛ پیاده‌سازی باید از وابستگی‌های موجود Spring/Java استفاده کند و وابستگی مستقل فقط با دلیل در مرحله پیاده‌سازی انتخاب شود.

### ذخیره‌سازی

- **تصمیم**: Spring Data JPA با H2 برای اجرای محلی و پروفایل اختیاری PostgreSQL.
- **دلیل**: این ترکیب مستقیماً در PRD آمده و نسخه‌ها، گزارش‌ها و اجراها باید باقی بمانند.
- **گزینه‌های بررسی‌شده**: حافظه‌ای/غیردائمی؛ با نگه‌داری تاریخچه موردنیاز سازگار نیست.

### کنترل دسترسی و سطح API

- **تصمیم**: Spring Security برای Bearer token مسیرهای `/api/admin/**`؛ مسیرهای عمومی فقط مقاله PUBLISHED را آشکار می‌کنند. قرارداد عمومی در OpenAPI مستند می‌شود.
- **دلیل**: احراز هویت ساده مدیر و پنهان‌ماندن وجود پیش‌نویس از الزامات‌اند.
- **گزینه‌های بررسی‌شده**: حساب کاربری یا نقش‌های چندگانه؛ خارج از محدوده نسخه نخست.

### نسخه‌بندی و انتشار

- **تصمیم**: هر snapshot مقاله شماره نسخه مستقل دارد؛ گزارش بازبینی به شماره نسخه ورودی متصل می‌شود. انتشار فقط با APPROVED همان نسخه فعلی ممکن است.
- **دلیل**: تأیید نسخه قدیمی نباید مجوز نسخه تازه شود.
- **گزینه‌های بررسی‌شده**: وضعیت تأیید کلی در سطح مقاله؛ نمی‌تواند شرط انتشار را ایمن تضمین کند.

## موارد حل‌نشده

برای طراحی نسخه نخست ابهام مسدودکننده‌ای باقی نمانده است. نشانی package base و نسخه دقیق وابستگی‌ها در فایل Maven هنگام آغاز پیاده‌سازی تعیین می‌شوند؛ PRD آن‌ها را تثبیت نکرده است.
